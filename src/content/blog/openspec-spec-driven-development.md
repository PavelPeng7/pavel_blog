## 背景

AI 编程助手越来越强大，但有一个核心痛点一直没有被解决：需求只存在于聊天历史里。告诉 AI "加一个暗黑模式"，它开始写代码，写到一半发现理解不对，于是重新解释。下一次打开项目，没有人记得当时为什么这么设计。

对于图形学、游戏开发这类场景更是如此——一个渲染特性如果需求没对齐，改起来比普通业务代码痛苦得多。所以我一直在找一种方法，能让 AI 在动手之前先搞清楚我要什么。

## OpenSpec 是什么

OpenSpec 是一套"先把需求写成可审核的 Spec 文档，再让 AI 按照 Spec 写代码"的工作流。

它的核心价值在于解决 AI 开发中的**对齐难题**：通过规范化的文档作为人与 AI 之间的契约，确保代码实现与需求意图保持一致。

适用场景：
- 有 PRD / 设计文档，需要转代码
- 已有系统，需要二次开发或扩展
- 需要与 AI 精确对齐实现细节
- 希望开发过程可记录、可回溯

## 我的 AI Coding 基本流程

我目前的工作流是四步走：

```
Repo Understand → Design → Plan (OpenSpec) → Implement (OpenSpec)
```

不管是从零开始的项目，还是基于已有代码架构的迭代，都走这个流程。OpenSpec 卡在 Plan 和 Implement 这两个环节。

## OpenSpec 四阶段标准流程

官方推荐的标准流程分为四个阶段，每个阶段都有明确的交付物：

### 1. Proposal（提案）
起草变更提案，明确：
- 为什么要做这个变更（业务价值、解决的痛点）
- 变更的范围和边界
- 预期的产出和验收标准

交付物：`proposal.md`

### 2. Review & Align（对齐）
团队或相关方对提案进行审核，确保需求理解一致、技术方案可行、风险已被识别。

这是整个流程中最关键的"人参与"环节——对齐之后才进入 AI 实施阶段。

### 3. Apply（实施）
AI 根据审核通过的 Spec 文档生成代码。由于需求已经被精确描述，这一阶段 AI 的产出质量和一致性会显著提升。

交付物：代码变更

### 4. Archive（归档）
变更实施完成后，将 `changes/` 下的提案合并更新到 `specs/` 目录，同时归档本次变更记录，确保系统规范始终与代码保持同步。

## 目录结构

OpenSpec 使用 `openspec/` 目录作为所有规格文档的统一入口：

```
openspec/
├── specs/                      # 当前系统的真实规格
│   └── <domain>/
│       └── spec.md
│
├── changes/                    # 所有变更提案
│   └── <change-name>/
│       ├── proposal.md         # 变更目的、范围、为什么做
│       ├── design.md           # 技术设计、实现思路
│       ├── tasks.md            # 实施任务清单
│       └── specs/              # 本次变更对应的 delta specs
│           └── <domain>/
│               └── spec.md     # 仅描述本次变更的增量修改
│
└── config.yaml                 # 项目级配置（可选）
```

核心设计是 `specs/` 与 `changes/` 分离：前者代表系统的"当前状态"，后者代表"待变更的提议"。每次变更经过完整的审核流程才能合并到主规范中。

## 轻量级变体：Opsx

完整四阶段流程对于小改动有点重。OpenSpec 提供了轻量级变体 **Opsx**，专为快速迭代场景设计：

| 指令 | 用途 |
|------|------|
| `/opsx:new` | 开启一个规范化变更（中等规模） |
| `/opsx:ff` | 快速处理极小改动（一行修复、配置调整） |
| `/opsx:apply` | 让变更正式生效，更新系统规范 |
| `/opsx:archive` | 收尾整理，归档变更记录 |

权衡：**速度 vs 可追溯性**。小改动可以快进，但涉及核心架构的变更，仍然建议走完整的四阶段流程。

## 在 Codex 中的使用

在 Codex 中使用 OpenSpec 不需要手动安装任何工具，只需在项目级或用户级的 `AGENT.md` 中加入遵守 OpenSpec 规范的规则，Codex 会自动识别并应用。

实测发现，Codex 对指令的匹配比较模糊，好处是记忆负担小，AI 还会主动引导你遵守规范：

- **提案**：`/openspec-proposal`、`/proposal`、`提案`
- **实施**：`/openspec-apply`、`/apply`、`实现`
- **归档**：`/openspec-archive`、`/archive`、`归档`

建议在项目初期就启用这一规范，而不是等到代码混乱后再补救。规范越早建立，后续的 AI 协作效率越高。

## 一些思考

对我而言，OpenSpec 最大的价值不是"规范"，而是**强迫我思考**。

开发中有个常见的错觉：我们以为自己想清楚了需求，但其实只是一个模糊的方向感。比如"做一个风格化水面的后处理"——这个词在不同的语境下意味着完全不同的东西。用 OpenSpec 把 spec 写清楚，不仅是给 AI 看的，更是给自己梳理思路的。
